# 青色帳簿の毎日の改善会議（10案 → レギュラー3人＋日替わりゲストで議論 → 5案）

## 対象
- アプリ：「F1肥育 青色帳簿」 https://claude.ai/artifact/WiWGTLS4MCWLEPc2Hgs6Kd
- 使う人：F1（交雑種）の牛を肥育している個人事業主。米も少し作っている。青色申告決算書（農業所得用）を自分で書く。
- 使う場面：牛舎の作業の合間にスマホで記帳することが多い。農協（JA）の購買明細書の写真を Claude に送って仕分けしてもらうこともある。
- 元は Apple Numbers の手作り集計ファイルだった。

## 本人が決めた仕分けのルール（変えない）
- スモール・仔牛の代金 → 素畜費（頭数も記録）
- 市場手数料・畜産運賃（導入のときも出荷のときも） → 荷造運賃手数料
- 出荷経費・出荷運賃手数料 → 荷造運賃手数料、奨励金・マルキン → 雑収入
- モーレット・ミルフィット・ミルク・配合飼料 → 飼料費
- ザクサ液剤など除草剤・薬 → 農薬・衛生費
- 農機用のエンジンオイル（JAオイル） → 諸材料費
- 金額は税込で記帳する。出荷の値段は（枝肉重量×単価＋内臓）×1.08。

## 手順

### 1. 材料を集める
- ユーザーから今日の「使った感想・困ったこと」があれば、それを最優先の材料にする。なければ一言だけ聞いてよい（定期実行のときは聞かずに進める）。
- アプリの今の作りを読む：Artifact ツールの `action: "read"` に上の URL を渡して HTML を取得する（WebFetch は使わない）。
- 記帳データの傾向を見る：ArtifactData で `entries`・`cattle` コレクションを list する。科目の偏り（雑費が多い、メモに「要確認」が残っている、未入力の月がある等）を弱点のヒントにする。データは読むだけで書き換えない。
- 前回までの会議記録を読み、同じ案を繰り返さない：ArtifactData で `kaizen` コレクションを list する（下の 7 を参照）。

### 2. 改善案を10個出す
- 実際に使われている会計・記帳アプリや農業アプリで効いている仕組みを参考にし、「どのアプリの何か」を必ず書く（例：freee のレシート撮影、やよいの青色申告オンラインの自動仕訳、マネーフォワードの仕訳ルール、JA の営農アプリ、家計簿アプリの定期入力 など）。
- 感想で出た不満を解決する案を、少なくとも2つ入れる。
- 確定申告の時期（1〜3月）が近いときは、決算書の作成・提出に直結する案を優先して入れる。
- 前回までに見送った案も候補にしてよい（状況が変わった理由を添える）。
- 各案は「何をするか／参考にしたアプリ／この帳簿ではどうするか」を1〜2行で書く。

### 3. 会議のメンバーを決める（レギュラー3人＋日替わりゲスト1〜2人）
レギュラー（毎日参加）：
- **使いやすさ担当**：スマホで片手で入力できるか、押す回数、画面のごちゃつき、文字の読みやすさ
- **青色申告担当**：決算書（農業所得用）の科目・棚卸・控除の扱いが正しいか、税務署に説明できる記録か、65万円控除の条件（複式簿記・e-Tax）に近づくか
- **技術担当**：実装の手間（小/中/大）、データが消えたり二重に入ったりしないか、今のコード（1枚の HTML・db 保存）との相性

日替わりゲスト（1〜2人。前回と違う人を選び、今日の10案に合う人を優先）：
- **税理士**：申告前にこの帳簿を受け取ったら困らないか
- **農協の担当者**：購買明細・精算書・マルキンとの突き合わせがしやすいか
- **牛舎作業中の本人**：手袋・汚れた手・短い休憩時間でも記帳できるか
- **スマホが苦手な家族**：説明なしで代わりに記帳できるか
- **辛口レビュアー**：あえて全案の弱点を突く反対役
- **税務調査の目線**：記録の根拠（日付・取引先・明細）が後から追えるか
- **ほかの肥育農家**：同じ立場の人が使っても役に立つか

会議の最初に、今日のゲストが誰で、なぜ選んだかを1行で書く。

### 4. メンバー全員をサブエージェントとして同時に立ち上げる
- 全員を1回の応答でまとめて起動し、同時に動かす。
- 全員に同じ10案、アプリの説明（上の「対象」「仕分けのルール」）、ユーザーの感想、アプリの HTML の要点を渡す。アプリやデータの編集はさせない。
- 各メンバーには次の4つを600字程度で出させる。
  1. 10案それぞれの短い評価
  2. 今すぐやるべきトップ5（順位付き）
  3. 落とした案の理由
  4. 他のメンバーへの反論・提案を1〜3個
- 全員の結果がそろうまで待つ。結果を予想して先に書かない。

### 5. 議長として結果をまとめる
- 全員の順位を表にする。
- 1位=5点〜5位=1点で合計し、上位5つを選ぶ。ゲストの票もレギュラーと同じ重さにする。
- 同点のときや意見が割れたときは、反論を読んで議長が判断する。2つの案を合わせてもよい。判断の理由は1行で書く。
- メンバーから出た条件（例：「今の記帳データを壊さない形で」「オン・オフできるように」）は、採用案に反映する。
- 青色申告担当が「税務上まずい」と言った案は、点数が高くても採用しない（理由を書く）。
- 辛口レビュアーが出た日は、その指摘への答えを各採用案に1行で添える。

### 6. 日本語で報告する
1. 今日のメンバー（ゲストと選んだ理由）
2. 全員の順位表
3. 今日の改善案ベスト5（各案：何をするか、なぜ良いか、手間、誰の意見を取り入れたか）
4. 見送った案と理由（短く）
5. おすすめの実装順

最後に「どれを実装しますか？」と聞く。**ユーザーが選ぶまで実装はしない。**

### 7. 記録を残す
ArtifactData で、アプリの `kaizen` コレクションに、その日の日付（`YYYY-MM-DD`）を doc_id にして1件書く。中身は `{date, ideas:[10案], members:[…], ranking:[…], top5:[…], rejected:[…]}` を短く。次回の重複防止用。
- 記録はアプリの中（本人しか見られない場所）に残す。公開リポジトリには金額や取引の中身を書かない。

## 注意
- 専門用語は使わず、簿記や IT に詳しくない人にも分かる言葉で書く。科目名など申告で使う言葉はそのまま使ってよい。
- 議論は「別々に評価した結果を議長がまとめる」形。実際より大げさに書かない。
- メンバーは全員同じAIなので、人数を増やすより、役割の違いをはっきりさせることを大事にする。
- 実装するときは1つずつ作り、確認してから次へ進む。記帳データを書き換える変更は、必ず先にユーザーに確認する。
